# 논문 정독 노트

정독일 2026-10-28. 원문(arXiv·ACL Anthology·CVF·공식 모델 카드) 기준. 수치는 원문 표의 값이며, 요약·초록 문구와 표가 다를 때는 표를 따름. 합성 데이터 결과와 실측 결과는 구분 표기.

구상안의 두 축에 맞춰 정리함.

- 1축: AI가 효율적·효과적으로 이해하는 비정형 데이터(표·이미지·기술문서)의 전처리·구조화
- 2축: 제한된 GPU·폐쇄망·온프레미스·엣지 환경에서 이를 LLM에 적용하는 방법

## 1축. 전처리·구조화

### 1.1 문서 변환 모델·도구

#### SmolDocling (arXiv 2503.11576)

- 문제: 문서 변환을 대형 VLM 또는 여러 전문 모델의 조합에 의존하는 구조.
- 방법: 2.56억 파라미터 단일 VLM(SigLIP 93M + SmolLM-2 135M). 출력은 DocTags(요소 태그 + 0~500 격자 위치 토큰 + OTSL 표 토큰). 512×512 패치당 64개 시각 토큰.
- 수치: DocLayNet 전체 페이지 OCR 편집거리 0.48(Qwen2.5-VL-7B 0.56, GOT 0.61). 표 TEDS FinTabNet 0.52(구조 0.81), PubTables-1M 0.65(구조 0.88). 레이아웃 mAP 0.231(사람 0.82). A100·vLLM 기준 쪽당 0.35초, VRAM 0.489GB. 최대 8,192토큰, 3쪽.
- 한계(원문 명시): 위치 태그 누락, 태그 미닫힘, 반복 생성, 72dpi 표 전사 저하.
- 반영: 통합 문서 모델은 "전체 페이지를 한 번에"가 아니라 영역 단위·검증 전제로 사용. 표는 구조(TEDS 0.81~0.88)와 내용(0.52~0.65)의 차이가 커서 셀 내용 검증이 필수.

#### Granite-Docling-258M (IBM 모델 카드, 2025-09)

- 구조: Idefics3 계열, SigLIP2-base-patch16-512 + Granite 165M. Apache 2.0.
- 수치(SmolDocling → Granite-Docling): 레이아웃 mAP 0.23→0.27, 전체 페이지 OCR 편집거리 0.48→0.45, 표 TEDS 구조 0.82→0.97·내용 0.76→0.96(FinTabNet 150dpi), 수식 F1 0.947→0.968, 코드 F1 0.915→0.988.
- 운용: docling CLI·SDK(VlmPipeline), transformers, vLLM(`--revision untied`), MLX, llama.cpp 커뮤니티 양자화. 다국어(일·아·중)는 실험 단계, 한국어 미지원 명시 없음.
- 한계: Docling 안에서 사용 권장, 안정화 조치에도 반복 생성 완전 제거 아님.
- 반영: 스캔본·이미지 영역의 1차 변환 후보. 표 내용 TEDS 0.96은 150dpi 금융 표 기준이므로 기술문서 다단 헤더 표에서는 별도 확인 필요.

#### Docling 기술 보고서 (arXiv 2408.09869)

- 구조: PDF 백엔드(docling-parse 또는 pypdfium) → 쪽별 레이아웃(RT-DETR 계열, 72dpi, CPU 1초 미만) → TableFormer(표당 CPU 2~6초) → 선택적 OCR(EasyOCR 216dpi, CPU 30초 이상) → 조립(읽기 순서·캡션 연결).
- 수치(225쪽, OCR 끔): M3 Max 4스레드 1.27~2.18쪽/초, Xeon E5-2690 4스레드 0.60~0.94쪽/초, 최대 메모리 2.4~6.2GB.
- 한계: pypdfium 백엔드는 빠르고 가벼우나 표 구조 품질 저하. 그림 안 텍스트는 버림.
- 반영: 텍스트 레이어가 있는 PDF는 GPU 없이 CPU 파이프라인으로 처리 가능. 그림 안 텍스트가 버려지므로 그림 영역에 한해 VLM으로 보완하는 선택적 전처리의 근거.

#### Nemotron-Parse 1.1 (arXiv 2511.20478) / Nemotron 3.5 Parse

- 구조: RADIO ViT-H/16(657M) + mBART 10층 디코더(256M), 총 885M. 출력은 Markdown + 클래스 + 경계 상자. TC 변형은 시각 토큰 3,200→833.
- 수치: OmniDocBench v1.0 영어 전체 오류 0.131(표 0.118), 토큰 3,201. TC 0.129, 토큰 833. 표 TEDS 82.7~86.2. H100 기준 약 4~5쪽/초.
- 한계: 한·중·일은 "제한적 지원" 명시. 학술·표준 PDF에 강함.
- 반영: 비교 실험 후보(OpenMDW 1.1 조건 확인). 시각 토큰 4분의 1로 줄여도 품질이 유지된다는 점은 2축(토큰 예산)의 근거.

#### OmniDocBench (CVPR 2025)

- 구성: 981쪽, 9종 문서, 병합 셀 표 150개, 흐린 스캔·워터마크·회전 속성.
- 수치: 전체 편집거리(영어) MinerU 0.15, Mathpix 0.191, GPT-4o 0.233, Qwen2-VL-72B 0.252, Marker 0.336. 표 TEDS MinerU 78.6, Qwen2-VL-72B 76.8, GPT-4o 72.0. 병합 셀이 있으면 대부분 하락(RapidTable 85.4→77.1, InternVL2-8B 78.4→58.7). 회전 표는 급락(GOT 76.3→8.5).
- 반영: 병합 셀·회전·흐린 스캔은 "불확실 영역"으로 분류해 재처리 대상에 넣는 기준. Docling은 이 벤치마크에 미포함.

#### PureDocBench (arXiv 2605.07492)

- 구성: 10개 도메인 1,475쪽을 Clean(렌더)·Digital(모사 열화)·Real(실물 촬영·재공유) 3판으로 동일 정답 4,425장. 공개 자료가 아닌 생성 문서라 학습 데이터 중복이 적음.
- 수치: 58개 모델, 최고 평균 79.69(GLM-5.3-Flash), 중앙값 66.2. Real은 Clean 대비 평균 11.61점 하락(파이프라인 특화 −14.2, 종단 특화 −13.0, 범용 VLM −9.3). 표 최고 87.35. 1.2B MinerU2.5-Pro 70.07 vs 1T급 Kimi K2.6 70.10, 4B 특화 모델 72.6~73.9.
- 반영: 스캔·촬영본은 별도 경로로 분류하고 재처리 여지를 둠. 소형 특화 모델이 범용 대형 모델과 동급이라는 점은 폐쇄망 모델 선택의 근거. 중국계 모델 결과가 다수이므로 수치는 경향으로만 인용.

#### ParseBench (arXiv 2604.08538)

- 구성: 기업 문서 1,180건 2,078쪽, 규칙 16.9만 개. 표(GriTS·레코드 일치)·차트(데이터 포인트)·본문 충실도·서식·근거 위치 5개 차원. 저자가 LlamaParse 개발사이므로 자사 결과는 제외하고 봄.
- 수치: 표는 Gemini 3 Flash 89.9, Azure 86.0, Extend 85.1, Docling 66.4. 차트는 전용 파서 0.9~6%(Reducto 57.0 제외) vs Gemini 3 Flash 64.8. 근거 위치는 전용 파서 61~74 vs VLM 최고 56, 소형 상용 VLM 6~7. Gemini 3.1 Pro 8.49¢/쪽(13배 비용)이 Flash 0.65¢/쪽보다 종합 점수 낮음.
- 반영: 요소 유형별 라우팅의 직접 근거. 표·위치는 파서, 차트는 VLM, 본문은 어느 쪽이든 90% 수준. 비용을 늘려도 정확도가 비례하지 않으므로 상위 모델 재처리는 게이트 통과 실패 건에 한정.

#### Arctic-Extract (Snowflake 기술 블로그, arXiv 2511.16470)

- Qwen2.5-VL 7B 기반, AWQ 4비트, 시각 토큰 4:1 병합으로 A4 1쪽 약 1,000토큰, A10 24GB에서 125쪽 처리. 중국계 기반이므로 도입 후보 아님. 토큰 병합·4비트 조합의 실무 사례로만 참고.

### 1.2 표 이해·표 표현·구조화 추출

#### MMTabReal (Findings ACL 2026)

- 구성: 실제 표 500개, 질의 4,021건, 표 안 이미지 11,836개(89%의 행에 이미지 포함).
- 수치(GPT-4o Mini, EM): 이미지 제거 24~39, 이미지를 사람이 검증한 텍스트로 치환 51~68, 표를 이미지로 입력 39~49, 삽입형 36~48. 사람 76~84. Qwen2.5-VL-7B 삽입형 18~36.
- 오류: 개방형 모델은 환각·구조 오류 비중이 큼(Qwen2.5-VL 환각 17.0%, 구조 13.5%).
- 반영: 표 안 시각 요소는 "검증된 텍스트 치환"이 모델 입력으로 가장 유리. 즉 적재 시점에 이미지→텍스트 치환을 하고 사람이 검증한 값이 가장 높은 정답률을 냄. 7B급 개방형 모델은 표 이미지 직접 입력 시 구조 오류가 커서 구조화 전처리가 필요.

#### Table Meets LLM (WSDM 2024, SUC 벤치마크)

- 수치: HTML이 CSV·TSV보다 6.76%p 우수. 7개 구조 과제(분할·조회·역조회·행렬 검색·크기·병합 셀 탐지) 최고 정확도 65.43%.
- 반영: LLM은 표 구조의 기본 인식부터 불완전함. 구조를 모델에 맡기지 않고 전처리에서 확정해 넘겨야 함.

#### Beyond Linearization: Attributed Table Graph (arXiv 2601.08444)

- 방법: 표를 행 앵커·열 헤더(간선 라벨)·셀 값 노드의 그래프로 두고, 질의 기반 Personalized PageRank로 관련 행·셀을 재배열. 학습 불필요, 표당 구성 0.01초.
- 수치: WikiTQ(LLaMA3.3-70B) ATG 80.1, HTML 77.3, LaTeX 76.3, Markdown 75.5, JSON 74.2. 구조 오류율 ATG 14.4% vs Markdown 21.6%. 행·열 섞기 시 하락 ATG −0.5, RoT −6.2, Table-Critic −18.7. 입력 토큰 ATG 약 4.7k vs RoT 2.0k vs Table-Critic 31.2k.
- 한계: 상위 단계에서 표 구조(행·열·셀 대응)가 복원되어 있어야 함. 다단 헤더는 경로("지역-근로자 유형-지표")로 평탄화.
- 반영: 구상안의 Subject/Attribute/Value 단위가 ATG의 행·헤더·셀 삼중항과 같은 구조. 다단 헤더를 속성 경로로 저장하는 방식의 근거. 질의 관련 행을 골라 넣는 Evidence Packet의 근거(전체 표 입력보다 토큰 적고 순서 교란에 강함).

#### TableRAG (EMNLP 2025)

- 문제: 표를 Markdown으로 잘라 청크 검색하면 전역 집계가 깨짐(예시: 20%가 50%로 답변).
- 방법: 오프라인에 표를 관계형 DB(MySQL)와 스키마 설명으로 저장, 청크는 원 스키마에 연결. 온라인에 질의 분해 → 텍스트 검색(상위 30→재순위 3) → 표 출처 청크면 SQL 실행 → 중간 답 생성, 최대 5회 반복.
- 수치: HeteQA 44.9(DeepSeek-V3) vs NaiveRAG 35.9, WikiTQ 80.4 vs 75.4. 지연 24.6초 vs ReAct 45.7초(HeteQA). 토큰 비용 미보고.
- 한계: 강한 백본 전제, 소형 모델에서 저하 가능성 명시.
- 반영: 저장(DB)·검색(서술문)·입력(Packet) 분리의 근거. 비교·집계 질의는 LLM이 아니라 저장소의 연산이 답을 만든다는 원칙.

#### ASTRA (ACL 2026, arXiv 2604.08999)

- 방법: 복잡한 표를 LLM이 "논리 의미 트리"로 재구성(헤더 정규화·숨은 계층 복원, 커버리지·구조 평가기로 재정제) → 텍스트 추론(트리 경로 탐색)과 기호 추론(트리 위 Python 코드 실행, 오류 시 자기 수정)을 병행하고 선택기가 답을 고름. 학습 불필요.
- 수치: AIT-QA 91.6, SSTQA 81.9, HiTab 90.1(DeepSeek-V3 평탄 직렬화 78.5·63.2·82.0, o3 89.1·78.2·85.3). Qwen3-8B 직접 프롬프트 52.8→트리 입력 60.9(SSTQA). 트리 구축 29~94초, 질의 6~12초, 표당 질의 3~10회부터 비용 회수.
- 한계: 단순 표는 재구성 비용이 들고 이득 없음. 구조 불일치가 오류의 36.7%. Llama3.1-8B 기호 추론 10.5%로 소형 모델 편차 큼.
- 반영: 적재 시점에 표의 계층을 한 번 복원해 두면 소형 모델도 이득을 본다는 근거. 단, 계산은 모델이 아니라 코드·SQL 실행에 맡기고 8B급의 코드 생성 오류는 자기 수정·검증으로 보완.

#### Beyond String Matching (arXiv 2603.18652)

- 방법: arXiv LaTeX 표를 합성 PDF에 삽입해 정답 확보, LLM 판정(0~10점)으로 의미 기준 평가. 518쌍 사람 평가와 대조.
- 수치: 사람 상관 Gemma-4-31B 판정 0.93, Claude Opus 4.6 0.94, TEDS 0.68, GriTS-Con 0.70. 복잡한 병합 셀 표에서 최대 2점 하락. LightOnOCR-2-1B 9.08(상위권).
- 발견: 규칙 지표는 헤더 평탄화·기호 표기 차이를 벌점하고 소수점·부호 누락은 거의 벌점하지 않음. 표를 통째로 놓치는 모델과 망가뜨리는 모델이 구분됨("놓치는 쪽이 낫다").
- 반영: 검증 3층에서 "형식"이 아니라 "값·단위·헤더 대응"을 기준으로 삼아야 함. PoC 지표에 TEDS와 별도로 값 일치율·오염률을 두는 근거.

#### ExtractBench (arXiv 2602.12247)

- 구성: PDF 35건, 2,076쪽, 정답 값 12,867개, 5개 도메인, 스키마 키 12~369개. 모델은 상용 6종(Gemini 3, GPT-5.x, Claude 4.5). 개방형 모델 미평가.
- 수치: 유효 JSON 51%(107/210), 필드 통과율 전체 4.6%, 최고 Gemini 3 Flash 6.9%(무효 출력을 0점 처리). 유효 출력 기준 72.9%. SEC 10-K(키 369개)는 전 모델 유효 출력 0%. 10-K 제외 시 통과율 28.0%.
- 발견: 실패 예측 변수는 문서 길이보다 스키마 폭과 출력량.
- 반영: 문서 전체를 큰 스키마 하나로 뽑는 방식은 성립하지 않음. 정보 단위를 작은 스키마(7필드)로 쪼개고 단위별로 검증하는 구상의 근거. 인용 시 "6.9%는 무효 출력 포함 필드 통과율, 유효 출력 기준 72.9%"로 병기.

#### LLMStructBench (arXiv 2602.14743) — 정정

- 내용: 자연어 메시지(이메일 5종, 995건)를 스키마 JSON으로 변환. 문서·표 입력이 아님. DOC_micro 0.52는 GPT-4o·Gemma3 27B의 "완전 정답 문서 비율(실패 할인)".
- 수치: 22개 개방형 모델 중 Gemma3 27B가 GPT-4o와 동급(종합 0.74). 소형(3.8B·1B)은 0.48~0.49. 값 오류는 모든 설정에서 잔존.
- 반영: 문서 추출 근거로 인용하면 안 됨. "개방형 27B가 상용 모델과 동급의 구조화 출력이 가능하나 값 검증은 별도로 필요"라는 2축 근거로만 사용.

#### Doc2DB-Bench (arXiv 2608.08459)

- 과제: 긴 문서(평균 4.3만 토큰)에서 관계형 DB 인스턴스 구축. 203건, 42개 스키마, 엔티티 표 117·관계 표 132.
- 수치(종합 F1): GPT-5.4 75.3, Claude Opus 4.6 73.6, Gemini 2.5 Pro 70.8, Qwen2.5-72B 36.1, Qwen2.5-14B 33.0, LLaMA-3.1-70B 14.3. 관계 추출이 엔티티보다 12~25점 낮음. 참조 무결성 위반 다수.
- 실패: 단위("천 단위" 표기 무시), 시간 한정어, 대명사·다중 엔티티 결합, "제외" 조항 무시.
- 반영: Qualifier(조건·시간·단위)와 Parent Context를 스키마 필드로 둔 설계의 근거. 개방형 70B급도 관계 추출은 취약하므로 관계는 LLM이 생성하지 않고 표 구조·조항 참조에서 규칙으로 도출.

### 1.3 공학 문서·도면

#### BLUEPRINT (arXiv 2602.13345)

- 환경: 레거시 문서관리 시스템 약 77만 파일(필터 후 55.9만, 도면 16.6만). 공개 불가 데이터.
- 방법: YOLOv8-S로 4개 영역(도면 번호·데이터 블록·부품 목록·개정 블록) 탐지(mAP 89.5%, A100 5.2ms) → 영역별 VLM OCR(Llama 4, 8비트 양자화, 해상도 제한, 스키마 검증) → 하이브리드 검색(BM25+밀집, z-score 융합) → 개정 불일치 벌점 재순위.
- 수치(5천 파일·질의 375건): Succ@3 0.715·nDCG@3 0.626 vs 최고 기준선 LLaMA 3.2 Vision 0.623·0.521. 영역 한정 OCR nDCG 0.563(예측 상자)·0.699(정답 상자) vs 전체 페이지 Tesseract 0.208·EasyOCR 0.287. 파일당 9.46초 vs Llama 4 Scout 64.36초.
- 한계: 판독 가능한 스캔·표준 표제란 전제. 질의 수 표기 불일치(350·375·370·325).
- 반영: "영역 탐지 → 영역 한정 소형 모델"이 전체 페이지 VLM보다 정확하고 7배 빠르다는 가장 직접적 근거. 인용 시 10.1%p가 아니라 Succ@3 0.715 vs 0.623(9.2%p)로 표기하거나 원문 초록 수치임을 명시.

#### Florence-2 미세조정 GD&T 추출 (arXiv 2411.03707)

- 방법: Florence-2 base(0.23B) 전체 미세조정, 실제 도면 400장, RTX 4090.
- 수치(검증 세트): F1 61.5%(정밀도 76.7, 재현율 51.3) vs GPT-4o 제로샷 35.5, Claude 3.5 Sonnet 40.4. GD&T 항목이 많을수록 재현율 하락.
- 한계: 별도 시험 세트 없음, 후처리에 GPT-4o-mini 사용, 재현율 51%.
- 반영: 도면 기호는 소형 특화 모델이 범용 대형 모델보다 낫다는 근거. 단, 재현율 51%는 "검증·보류" 없이는 쓸 수 없는 수준.

#### 교량 도면 표제란 추출 (EC3 2026, Qwen2.5-VL-3B LoRA)

- 수치: 표제란 탐지 F1 93.8%(YOLOv11-m 93.1%), 제로샷 0%. 필드 추출 단어 정확도 기계 인쇄 0.78·손글씨 0.83. RTX A5000에서 도면당 탐지 2.97초, 크롭당 추출 8.91초, GPU 메모리 10GB 미만.
- 반영: 중국계 모델이라 도입 후보는 아니나, "탐지 + 크롭 추출" 2단 구성과 3B급 온프레미스 가능성의 사례.

#### P&ID 규정 검사 (EC3 2026, Youn 외)

- 수치: DXF 규칙 파싱 F1 100%(A104)·97.5%(4장) vs Claude Sonnet 4.5 이미지 입력 55.9%(선 48%). LLM은 검증 코드 생성에만 사용.
- 반영: 원본이 CAD 네이티브면 LLM 없이 파싱하는 것이 정답. "경로 선택" 표의 첫 행(원본 직접 파싱 우선) 근거. 이미지 PDF는 미처리라는 한계도 명시.

#### MechVQA (arXiv 2605.30794)

- 구성: 기계 도면 3,281장, 질의 20,778건, 10개 하위 과제(치수·주석, 텍스트·표, 조립 관계, 투영·다시점, 이상 탐지 등).
- 수치: 개방형 Qwen3-VL-32B 76.5, Gemma-3-27B 42.7, Llama-3.2-11B-Vision 25.5. 4B 모델을 SFT+RL로 84.9까지 향상(기본 60.2).
- 실패: 밀집 시트의 결정적 주석 누락, 다시점 추론 불안정, 수치는 그럴듯하나 기하 제약 위반.
- 반영: 도면 이해는 범용 소형 VLM으로는 불가하고 특화 학습이 필요. 구상안에서는 도면을 "추론" 대상이 아니라 "영역별 값 추출 + 규칙 검증" 대상으로 한정.

#### Enginuity (arXiv 2606.03410)

- 구성: 군용 정비 교범 10권의 분해도·부품표 쌍 2,056건.
- 수치: 부품 번호 재현율 0.61~0.87이나 설명·수량까지 맞춘 토큰 F1은 0.03~0.18. OCR+정규식 기준선 재현율 0.012.
- 반영: 그림의 번호 표기(콜아웃)와 떨어진 표를 연결하는 과제가 아직 미해결. 구상안의 "그림↔표 소속 관계"는 모델 추론이 아니라 식별자 일치 규칙으로 연결.

#### DesignQA (arXiv 2404.07917)

- 구성: FSAE 규정 140쪽, 1,451문항(규칙 추출 1,222·이해 93·준수 136).
- 수치: 전체 문서 입력(GPT-4o) 규칙 조회 0.885 vs RAG 0.186. 정의 과제 최고 0.540(기준 0.358). 축척 막대 치수 0.28 vs 직접 치수 0.66(GPT-4).
- 발견: 단순 RAG는 관련 규칙 공급에 실패. 표는 평문으로 투입되어 행 간 비교 오류. 관련 근거를 보장해도(GuaranteedRAG) 조회 외 과제는 소폭 개선.
- 반영: "검색이 근거를 완전히 가져오는가"가 성능의 1차 결정 요인. 질문 유형별 최소 충분 근거(Packet) 설계와 근거 완전성 지표의 근거.

#### GEMS-RAG (arXiv 2610.33277)

- 구성: MUTCD 11판. 노드 8,240(부·장·절·청크·그림 485·표 68·장치), 간선 18,245(contains·cites·mentions·depicts·defines 등).
- 방법: 밀집+희소(BGE-M3) RRF → 식별자 그래프 근접도·규칙 유형 가중(Standard 1.2, Guidance 1.0, Option 0.9, Support 0.7)·계층 사전확률 → 교차 인코더 재순위 → 질의 라우터가 시각 근거 필요 판단 → 그래프 연결 그림 + ColQwen2 검색 → VLM 필터(최대 4개).
- 수치(150문항, 85건이 그림·표 근거 필요): Recall@5 86.7~88.0%, 근거 충분성 93.3%, 문맥 정밀도 50% 미만. 재순위 제거 시 −4.65점, VLM 필터 제거 −0.02, 계층 사전확률 제거 −0.22. GraphRAG는 BM25보다 못함.
- 한계: 단일 규정집, 판정·구축에 상용 모델 사용, 사람 검증 미완.
- 반영: 그래프는 "참조 관계 추적(조항→그림·표)"과 "규칙 유형 가중"에 쓰일 때 유효. 범용 GraphRAG보다 문서 구조 그래프가 낫다는 점. 재순위가 가장 중요한 구성요소라는 점은 2축에서 소형 재순위 모델의 가치로 연결.

#### Drawing-Checker (Procedia CIRP 142, 2026)

- 서지는 확인. 원문 접근 불가. "500개 사례" 미검증. 검색 결과로 나온 Brunel 저장소 PDF는 다른 논문(Chen·Cheng, 기계 도면 감사 P-C-C 참조 구조, 종단 구현 없음)이므로 인용하지 않음.

#### 기술 도면 분석의 인간-기계 협업 (IEEE SMC 2025, Chalmers)

- 배관 등각도 60장, 5개 LMM. Claude 3.5 Sonnet·GPT-4o 약 70%, 개방형 모델은 복잡 레이아웃·모호한 시각 정보에서 실패.
- 반영: 개방형 모델로 운영하는 환경에서는 사람 검토 경로가 설계에 포함되어야 함.

### 1.4 추출 결과 검증

#### RaV-IDP (arXiv 2604.23644)

- 방법: 추출물을 다시 렌더링(표→HTML→이미지)해 원본 크롭과 비교(SSIM 0.4 + 구조 0.6; 구조 = 행·열 수 0.2 + 셀 CER 0.8). 텍스트는 1−CER, 이미지는 지각 해시. 임계값 미달 건에 한해 상위 비전 모델로 재처리(최대 2회), 그래도 실패하면 저신뢰 표시로 보존. 원칙: 비교 기준은 항상 원본 영역, 추출물이 아님.
- 수치: 표 게이트 F1 0.914(정밀도 0.891, 재현율 0.939, τ=0.43). 충실도와 품질 상관 ρ 0.800(표)·0.877(네이티브 텍스트). 선택적 재처리로 비용 71% 절감, 통과율 61.2→76.0%. 종단 QA 개선은 미미(+0.0018).
- 한계: 추출기와 재구성기가 같은 OCR 오류를 공유하면 탐지 불가. 저대비 크롭 오경보.
- 반영: 구상안 검증 3층 중 "원본 근거 층"의 구체 방법. 재처리 대상을 게이트로 고르면 상위 모델 호출을 대폭 줄인다는 점이 2축과 직결.

#### DOCR-Inspector (arXiv 2512.10619)

- 방법: 문서 파싱 출력의 오류를 28개 유형(텍스트·표·수식, 11개 상위 수준)으로 탐지하는 7B VLM(Qwen2.5-VL-7B 기반, 체크리스트 추론 + GRPO).
- 수치(실제 882건): 사례 F1 텍스트 96.4·표 86.4·수식 85.4. 오류 유형 F1 텍스트 80.2·표 62.1. 피드백으로 재정제 시 dots.ocr 표 TEDS 75.4→79.8.
- 반영: 검증을 "점수"가 아니라 "오류 유형"으로 내면 재처리 경로를 유형별로 고를 수 있음. 표 오류 유형 F1 62%는 표 검증이 여전히 가장 어렵다는 뜻.

### 1.5 검색·RAG 구성

#### ViDoRe V3 (ACL 2026)

- 구성: 10개 코퍼스 약 2.6만 쪽, 질의 3,099건(사람 검증), 산업 정비(USAF 기술 교범 5,200쪽) 포함.
- 수치(nDCG@10): 시각 검색기 ColEmbed-3B-v2 59.8, 텍스트 Qwen3-8B 51.0, BM25 20.3. 텍스트 재순위(zerank-2) +13.2점, 시각 재순위 효과 없음. 하이브리드(시각 5 + 텍스트 5) F1 30.2 vs 시각 27.8·텍스트 25.0. 내용 유형별 텍스트 59.3 > 차트 56.3 > 표 53.9 > 이미지 49.3 > 혼합 45.1. 관련 쪽 20장 이상이면 약 39. 생성: 어려운 질의에서 이미지 문맥이 텍스트보다 2.4~2.8점 우위, 하이브리드 54.7%. 시각 근거 위치 F1 0.065~0.089(사람 0.602).
- 반영: 표·혼합 쪽에서 검색이 가장 약하므로 표는 별도 저장소로 분리. 재순위는 텍스트 측에서 효과가 크므로 구조화 단위의 서술문에 재순위 적용. 근거 위치(bbox) 제시는 모델이 못 하므로 전처리 시 Provenance를 기록해 둬야 함.

#### ColPali (arXiv 2407.01449)

- 수치: ViDoRe v1 nDCG@5 81.3 vs OCR+BGE-M3 66.1. 색인 쪽당 0.39초 vs 비구조화 파이프라인 7.22초(L4). 저장 쪽당 약 257.5KB(1,024 패치×128차원) vs BGE-M3 8.6KB. 토큰 풀링 3배 시 97.8% 성능 유지.
- 반영: 시각 검색은 색인이 빠르나 저장이 30배. 폐쇄망 저장·검색 비용에서 구조화 단위 + 텍스트 검색이 유리하다는 비교 근거. PaliGemma 기반이라 도입 가능 계열이나 구상안은 텍스트 검색을 기본으로 둠.

#### Graph·멀티모달 보강의 통제 평가 (arXiv 2607.16604)

- 조건: 텍스트 검색 기본 / +KG(삼중항을 프롬프트에 첨부) / +KGret(그래프로 검색 확장, 삼중항 미첨부) / +멀티모달 / 둘 다. 생성기 4종.
- 수치: HotpotQA 브리지 근거 완전성 0.22→0.46(+KGret), 정확도 0.485→0.655, +KG는 0.505·충실도 저하(0.435→0.375). SPIQA 교차 논문 완전성 0.50→0.72. 근거 완전 질의에서는 효과 없음. +KGret 추가 토큰 170~200. 멀티모달 프롬프트 861~9,477토큰. 픽셀 전용 그림 질의는 텍스트 0, 멀티모달 0.057~0.114(검색 상한 Recall@1 0.229).
- 반영: 관계 정보는 프롬프트가 아니라 검색 확장(조항→표·그림 1홉)에 사용. 근거 완전성을 PoC 지표로 채택. 캡션으로 답할 수 있는 그림은 캡션 텍스트화가 곧 해법.

#### GraphRAG-Bench: When to use Graphs in RAG (ICLR 2026)

- 구성: 의료 지침(NCCN)·소설, 4,076문항, 4단계(사실 조회·복합 추론·요약·창작).
- 수치(GPT-4o-mini, 소설/의료): 사실 조회 재순위 RAG 60.9/64.7 vs HippoRAG2 60.1/66.3, MS-GraphRAG local 49.3/38.6. 복합 추론 HippoRAG2 53.4/62.0 vs RAG 42.9/58.6. 프롬프트 토큰 RAG 879, HippoRAG2 1,008, LightRAG 10만, MS-GraphRAG global 33만. 색인 비용 MS-GraphRAG 약 65.5만 토큰(5.6만 토큰 소설 1권). 모델 3B에서 그래프 이점 1점 미만, 14B에서 4.8점.
- 지침: 정밀 검색, 큰 그래프가 아닌 좋은 그래프, 문맥 증가 제한.
- 반영: 폐쇄망 소형 모델 환경에서 범용 GraphRAG는 비용 대비 효과가 없음. 관계는 문서 구조(절·표·그림 참조)에서 결정적으로 얻고 LLM 추출 그래프는 만들지 않음.

#### SURE-RAG (arXiv 2605.03534)

- 핵심: 관련성과 충분성은 다름. 개별 문단 점수를 max·mean으로 합치면 빠진 홉을 놓치거나 반박 근거가 희석됨. 근거 집합 전체에 대해 지지·반박·불충분 3분류.
- 방법: DeBERTa-v3-base 교차 인코더(주장·문단 쌍) → 커버리지·관계 강도·불확실도·검색 신뢰 특징 → 로지스틱 회귀 집계. 지지 확률이 임계값 이상일 때 답하고 아니면 보류.
- 수치(HotpotQA-RAG v3): Macro-F1 0.908 vs mean-pool 0.652, GPT-4o 판정 0.728. 응답률 30%에서 위험 0.259→0.164(−37%). 응답률 70%에서는 이점 없음.
- 한계: 통제 벤치마크, 단답형, 문단 간 추론 없음. 실제 환각 탐지(HaluBench)로는 전이되지 않음.
- 반영: Evidence Packet 조립 뒤 "충분성 판정 → 보류" 단계를 둠. 소형 교차 인코더로 가능하므로 2축에 부담 없음. 보류 비율과 오답 위험의 상충을 PoC 지표로 둠.

#### 조사 논문 2편

- 시각 문서 RAG에서 MLLM의 역할(arXiv 2601.03262): 캡션 변환형·멀티모달 임베더·종단 표현형 3분류. 임베더는 CLIP 대비 인코딩 478ms vs 92ms, 저장 5배. 열린 과제로 "적응적 검색 단위(쪽↔요소)"와 소형 문서 특화 모델.
- 문서 이해 멀티모달 RAG 조사(arXiv 2510.15253): OCR 기반은 구조 손실, 종단 VLM은 문맥 모델링 취약. 시각 토큰이 텍스트보다 수십 배 많은 점이 효율 병목.

## 2축. 제한 환경에서의 LLM 적용

### 2.1 소형 모델 설계

#### SmolVLM (arXiv 2504.05299)

- 수치: 256M/500M/2.2B 추론 RAM 0.8/1.2/4.9GB(Qwen2-VL-2B 13.7GB). DocVQA 58.3/70.5/80.0, OCRBench 52.6/61.0/72.9. 512×512 이미지 1장 1,024토큰. 소형 모델은 픽셀 셔플 r=4(16배 압축)가 유리하나 OCR 같은 정밀 위치 과제는 손해. 소형 LM은 8k 토큰 초과 시 불안정.
- 반영: 소형 VLM에 긴 문맥을 주면 안 되므로 "쪽 전체"가 아니라 "영역 크롭"을 주는 설계. 2.2B 모델이 5GB 메모리로 DocVQA 80점이라는 점은 GPU 1장 공유 환경의 적재 처리 후보 근거.

#### DocSLM (arXiv 2511.11313, CVPR 2026 Findings)

- 방법: 쪽당 시각·OCR·레이아웃을 576토큰으로 압축(3,210→576, 5.6배), 긴 문서는 구간별 순차 처리 후 KV 캐시 해제·불확실도 최저 답 선택.
- 수치: MP-DocVQA 메모리 29.2→14.2GB, 지연 32.1ms vs InternVL2+RAG 113.4ms. 120쪽까지 메모리 14.2GB 고정(8B 기준선은 20쪽에서 75GB·120쪽 OOM). 스냅드래곤 NPU에 8비트로 배포.
- 반영: "쪽당 토큰 상한"과 "구간 처리 후 캐시 해제"는 소형 GPU에서 긴 문서를 다루는 두 원칙. 구상안의 Packet 토큰 예산과 같은 발상. Qwen2.5-1.5B 기반이므로 도입 대상은 아님.

#### PixelPrune (arXiv 2604.00886)

- 방법: ViT 입력 전에 32×32 블록을 이웃 블록으로 예측해 같으면 제거(PNG 예측 부호화 원리). 정확 일치면 픽셀 무손실, 학습 불필요, 좌표 보존.
- 수치: 문서·GUI에서 픽셀 고유 패치 22~71%. 문서 벤치 토큰 23~50% 감축에 정확도 −0.2~−0.9(Qwen3-VL 2B/4B/8B). TTFT 최대 4.2배, MMLongBench-Doc 3.0배·KV 캐시 45~63% 절감. 차트는 민감.
- 반영: 기술문서는 여백·반복이 많아 무손실 감축 여지가 큼. 2축에서 "시각 토큰 감축은 무손실 방식부터"라는 순서의 근거.

#### FastOCR (arXiv 2605.17447)

- 방법: KV 캐시는 그대로 두고, 디코딩 단계마다 주의를 두는 시각 토큰을 5~25%로 제한(초점 층 10%에서 선별, 다음 단계에 재사용).
- 수치: OmniDocBench 정확도 유지 98.0%(τ=0.05)·99.5%(τ=0.25). 토큰 삭제형(FastV 10.7, H2O 7.9, PyramidKV 19.1 vs 원본 72.8)은 문서 OCR을 파괴. 주의 지연 1.9~3.0배, 종단 1.2~1.4배 개선. 메모리 절감 없음.
- 반영: 문서 모델에서는 시각 토큰 영구 삭제가 불가하다는 근거. 메모리가 병목인 환경에는 효과가 없으므로, 메모리는 쪽당 토큰 상한·구간 처리(DocSLM)로, 지연은 주의 희소화로 나눠 대응.

### 2.2 양자화

#### SPEED-Q (arXiv 2511.08914)

- 방법: 1~2B VLM의 ViT·LLM 모두 저비트(4·2비트) 가중치 양자화. 단계별(ViT → 프로젝터 → LLM 공동) + 자기 증류.
- 수치(OCRBench, BF16→4비트→2비트): InternVL3-1B 79.7→79.7→58.5, InternVL3-2B 83.6→82.4→64.9, InternVL3-8B 88.2→84.6→75.8. 평균 하락 4비트 약 3%, 2비트 약 15%. 모델 크기 InternVL3-1B 1,790→485→315MB. 갤럭시 S25 런타임 메모리 1,855→527MB(4비트).
- 한계: 지연·처리량 미보고, 학습 비용(A100 8장 36시간).
- 반영: 적재 시점 모델은 4비트까지가 정확도 안전선. 2비트는 검증 통과율이 떨어져 재처리 비용이 늘어 총비용이 역전될 수 있음.

#### LQA (arXiv 2602.07849)

- CLIP 분류 과제의 양자화·적응 연구. 문서·OCR 평가 없음. 3비트 이하에서 정확도 붕괴라는 일반 관찰을 참고. 구상안 근거로 사용하지 않음.

### 2.3 질의 시점 비용: KV 캐시 재사용

#### FusionRAG: From Prefix Cache to Fusion RAG Cache (arXiv 2601.12904)

- 문제: 접두 캐시는 프롬프트 앞부분이 정확히 같을 때 유효. 검색 청크가 순서·조합이 바뀌면 캐시 실패.
- 방법: 청크별 KV를 유사 청크와 함께 미리 계산(오프라인, 청크당 0.218초), 질의 시 주의 점수 상위 15% 토큰을 재계산.
- 수치: 약 27k 토큰 문맥에서 첫 토큰 지연 2.66~9.39배 단축, 동시 부하 처리량 1.2~4.3배. 20개 설정 중 12개에서 전체 주의 품질의 80% 이상 회복. 쓰기 한 번·읽기 한 번 코퍼스에는 부적합.
- 반영: 자주 조회되는 구조화 단위(표준·사양)는 KV를 미리 계산해 두면 질의 비용이 줄어듦. 단, 품질 손실이 있어 조회형 질문에만 적용.

#### 청크 단위 KV 캐시 재사용 비교 연구 (arXiv 2603.20218)

- 수치: 기본 재사용(재계산 0)은 전체 프리필 대비 크게 하락. CacheBlend(15% 재계산)도 7~18% 하락. 주의 싱크 보정(Link0·APE)만으로도 기본 재사용보다 개선. 7~8B 모델·단일 질의 평가, 지연 미측정.
- 반영: KV 재사용은 "정확도 손실을 감수할 수 있는 조회형"에 한정하고, 비교·설명형은 전체 프리필 유지. 구상안에서는 선택 사항으로만 둠.

#### KV 캐시 압축 벤치마크 (arXiv 2607.05399)

- 비교: 전체 FP16, KIVI 2·4비트, TurboQuant 3·4비트, SnapKV(가지치기), CaM(병합). Llama-3.1-8B·Mistral-7B, A100 40GB.
- 수치: 압축률 KIVI2 약 5.2배, KIVI4 약 3.2배, SnapKV 4.0배, CaM 1.0~14.2배. QA는 대체로 유지(SnapKV·CaM이 다중 문서 QA에서 오히려 상승)되나 요약은 SnapKV −15%, CaM −35%, TurboQuant는 Multi-News 27.2→16.4. TurboQuant는 TTFT 1.5배 증가.
- 결론: 압축률은 성능 예측 변수가 아님. 미지 부하에는 KIVI4가 안정적, 처리량 우선이면 SnapKV, 요약·전역 문맥 과제는 전체 캐시 유지.
- 반영: 2축에서 KV 압축은 "조회형 질문에 4비트 KV 양자화"로 한정하고, 설명·요약형은 전체 캐시. 어떤 압축이든 자체 질의 집합으로 실측 후 채택.

### 2.4 온프레미스 RAG 사례

#### RAGnaroX (arXiv 2604.03291)

- 환경: RTX 4090 24GB, 64GB RAM, llama.cpp, Rust 마이크로서비스. Qwen3-4B q8 생성, multilingual-e5-large 임베딩, bge-reranker-v2-m3 재순위, 350토큰 청크 상위 3.
- 수치: 단일 홉 문맥 정밀도 0.90·재현율 0.94, 다중 홉 0.42·0.52. Qwen3-4B 충실도 0.859(14B보다 높음). 실무 250문항 Recall@10 0.83 vs 상용(Azure) 0.90. 5B 미만 모델 지연 2.5초 미만. 생성기 VRAM 7.5~17.9GB.
- 교훈: Markdown 변환 후 제목 단위 분할, 표 청크에 헤더 유지. 작은 모델이 근거 충돌 시 매개변수 지식에 덜 의존해 충실도가 높음.
- 반영: 2축의 기본 구성(양자화 4B 생성 + 소형 임베딩 + 소형 재순위)이 단일 GPU에서 성립. 다중 홉 약점은 1축의 관계 보존 구조화로 보완한다는 논리.

#### RAGAL (arXiv 2607.18756)

- 환경: 루마니아 농촌투자지원청 기술지원팀. 데이터 반출 0, 사람이 실행(읽기 전용 권한), 개발은 RTX 2000 Ada 8GB 노트북, 운영은 RTX 5060 8GB + RAM 64GB. Ollama, pgvector, bge-m3 임베딩, Gemma 3 12B 3비트(Q3_K_M) 생성. 파일럿 운영 중.
- 수치: 하이브리드 검색(RRF) + 의도 라우팅으로 내부 평가 62→81%(미세조정 전). bge-m3 전체 미세조정(72분)으로 티켓 recall@10 0.663→0.850, MRR@20 0.489→0.684. 단일 도메인 조정이 문서 도메인을 0.881→0.849로 조용히 떨어뜨림(합성 질의 추가로 복구). 3비트를 VRAM에 전부 올린 쪽이 CPU로 넘친 전정밀도보다 정확(48/48)하고 지연 수분→12.6초.
- 교훈(원문 13개 중): 생성기보다 검색 먼저, 도메인별 평가 세트 먼저, 소형 비전 LLM은 OCR로 신뢰 불가(내용 조작), 서빙 기본값(문맥 창 미설정)이 모델 동작의 일부, 양자화는 자체 평가로 판단, 대형 판정기는 보조 의견.
- 반영: 2축의 하드웨어 하한(8GB)과 운용 원칙의 실증. "소형 VLM을 OCR로 쓰지 않는다"는 교훈은 1축에서 직접 파싱 우선·VLM 한정 사용과 일치.

#### 철도 공학 RAG 사례 (arXiv 2607.01244)

- 환경: UNISIG 규격 3종(SUBSET-026 701쪽 등), 7B 이하 제약, L40 1장. 1~2판 Zephyr-7B, 3판 gemma-3-4b-it. Unstructured(hi_res) 파싱, 표 보존·이미지 폐기.
- 변화: 2판에서 의미 검색+BM25 앙상블, 3판에서 표를 캡션·사람 작성 요약과 함께 별도 청크로 분리. 평가단 평균 1.25→2.69→3.21(4점 만점), 4점 비율 23→39→62%.
- 양자화: 4비트 NF4 후 ROUGE는 하락, 사람 평가는 상승. 긴 표는 여전히 약점, 그림·도해 질문 불가.
- 반영: 표를 본문과 분리해 요약·캡션과 함께 두는 것만으로 평가가 크게 오름. 구상안의 표 단위 분리·서술문 생성의 실무 근거. ROUGE와 사람 평가의 괴리는 평가 설계(값 일치·근거 완전성 + 사람 검토)의 근거.

#### 온프레미스 RAG 청사진 (arXiv 2604.01395)

- 설계 논문(Docker Compose, Chroma·SQLite·MinIO, OpenTelemetry). 평가 미완. 가드레일·질의 정제·답변 검증 단계가 지연을 늘린다는 언급만 참고.

## 4. 미확인·주의 사항

- Drawing-Checker 원문 미확인. 수치 인용 금지.
- LLMStructBench는 문서 추출 벤치마크가 아님. 기존 인용 문구 정정.
- ExtractBench 6.9%는 무효 출력 포함 필드 통과율. 유효 출력 기준 72.9%와 병기.
- BLUEPRINT 수치는 질의 수 표기가 불일치. Succ@3 0.715 vs 0.623으로 인용.
- GEMS-RAG·MechVQA·DocSLM·Arctic-Extract·DOCR-Inspector·교량 표제란 연구는 Qwen 계열 모델 사용. 연구 근거로 인용, 도입 후보 아님.
- MMTabReal 하락폭은 초록 20~40%·서론 10~30%로 불일치. 표 수치(EM)로 인용.
- PureDocBench·ParseBench 상위권은 중국계·상용 모델이 다수. 경향(특화 소형 ≈ 범용 대형, 요소별 강점 분화)만 인용.
- ParseBench 저자는 LlamaParse 개발사. 자사 결과는 제외.
- Granite-Docling 표 TEDS 0.96은 FinTabNet 150dpi 기준. 기술문서 표에 그대로 적용 불가.
- 합성 데이터 결과(Beyond String Matching, Doc2DB-Bench 문서, 자체 PoC)는 실측과 구분.
